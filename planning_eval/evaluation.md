# Planning Evaluation

This folder contains the evaluation suite for the Sterling & Vance Bank Planning Agent.

## Evaluation Requests

Realistic banking investigation requests will be stored in:

```text
test_requests.json
```

The test suite contains real requests designed to exercise the different planning behaviors and provide a fair comparison between the supported methods.

The test cases should include:

* cases that favor decomposition-first planning
* cases where dynamic decomposition can react to new observations
* cases requiring lookahead or comparison of multiple alternatives
* cases where repeated attempts and cross-trial memory are useful
* cases where grounded external feedback is important for the final decision

## Evaluation Runner

```text
run_evaluation.py
```

The evaluation runner executes the applicable planning methods against the evaluation requests and records their results and execution traces.

## Metrics

```text
metrics.py
```

This module calculates the evaluation metrics from the collected results.

The main metrics are:

* task success / accuracy
* total LLM calls
* total tokens
* latency
* estimated cost per run

## Correctness

**`correctness.py`** — Provides deterministic, rule-based evaluation of each method's output against the expected facts defined in `test_requests.json`, measuring factual correctness without using an additional LLM judge.

## Artifacts

Each evaluation run will save its execution traces under:

```text
artifacts/
```

The artifacts provide the traces and evidence supporting the comparison tables

## Structure

The expected structure is:

```text
planning_eval/
├── evaluation.md
├── test_requests.json
├── run_evaluation.py
├── correctness.py
├── metrics.py
└── artifacts/
```

`artifacts/` is generated by the evaluation runner when the evaluation is executed.

## 9. Interpretation

The evaluation compares planning strategies using factual task success, LLM resource usage, latency, and estimated cost.

Task success is intentionally displayed as `matched/expected` in aggregate tables, for example `14/20`, rather than being collapsed into a 0–100 percentage.

Grounded methods are considered meaningfully grounded only when their environment validates candidate conclusions against the actual Sterling & Vance banking environment.

The deterministic correctness evaluator does not call an additional LLM.

### Method Selection and Justification

For the top-level investigation, the evaluation shows a clear trade-off between decomposition-first and dynamic decomposition. Decomposition-first achieved higher evidence recovery (7/14) than dynamic decomposition (4/14), but required substantially more LLM calls (12.5 vs. 5.5), tokens (23,822 vs. 5,536), latency (41.171s vs. 9.605s), and estimated cost ($0.003512 vs. $0.000807 per run). Therefore, decomposition-first is preferred when evidence completeness is more important, while dynamic decomposition is more resource-efficient. The current results do not justify declaring dynamic decomposition strictly better; instead, they support using decomposition-first for investigations where recovering all required evidence is the priority.

For lookahead reasoning, Plan-and-Solve performed best in the current evaluation, achieving 6/8 expected evidence items with only one LLM call, compared with 5/8 for Tree of Thoughts using nine calls. Plan-and-Solve also used fewer tokens and had lower latency and cost. Therefore, Plan-and-Solve is selected as the default method for the evaluated lookahead investigation because the measured results provide better correctness with substantially lower computational overhead.

For LATS, the evaluation provides an important grounding result. Ungrounded LATS achieved 2/10, while grounded LATS also achieved 2/10. Grounded LATS therefore did not improve measured correctness in this evaluation, while increasing LLM calls from 2 to 10, tokens from 522 to 6,926, latency from 2.957s to 29.544s, and estimated cost from $0.000087 to $0.001378 per run. Consequently, the current results do not justify selecting LATS as the default planning method. Grounded LATS is retained as an experimental option because its environment validation provides a stronger safety mechanism, but its benefit was not demonstrated by the current correctness scores.

These choices are based on the measured evaluation results rather than assumptions about which planning strategy should perform better. The tables above provide the empirical justification for the selected methods.
